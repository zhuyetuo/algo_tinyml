# 烧录到 GR5513，以及烧完先看什么

板子到手之后照这个走。前提是已经用 `./release.sh` 出过一份产物
（`release/<日期>_<提交>/`，里面有 `.hex`、`.bin` 和一份 README）。

## 0. 先确认手上这份产物是什么

打开产物目录里的 `README.md`，看两行：

- **模型指纹**：`tm_model.c+h` 的 sha256 前 16 位。
  板子上烧的是哪一份模型，只有这个数说得准——换一份模型重新导出，
  文件名一模一样，覆盖掉了没人知道。
- **代码提交**：带 `-dirty` 说明出包时工作区有未提交的改动，那份产物**复现不了**。
  要长期留着的版本，先提交干净再出包。

## 1. 烧

两条路，选一条。

### GProgrammer（Goodix 官方工具，推荐）

1. 板子用 USB 接上，或者 J-Link 接 SWD（SWCLK / SWDIO / GND / 3V3）。
2. 打开 GProgrammer → Firmware → 选 `tinyml_app.hex`。
3. 点 Download。

`.hex` 里带地址信息，不用自己填烧录地址——**这是推荐它的主要原因**，
地址填错是这一步最常见的错误，而且烧完不报错，只是启动不起来。

### J-Link 命令行

```bash
JLinkExe -device GR5513 -if SWD -speed 4000
# 在 J-Link 提示符里：
#   connect
#   loadbin tinyml_app.bin 0x01000000
#   r
#   g
```

`0x01000000` 是 GR551x 的 flash 映射起始地址。**用 `.bin` 就必须自己给地址**，
给错了烧进去也不会报错，只是板子起不来。

## 2. 接串口，波特率 115200

GR5513 的 log 从 UART 出来。引脚看 `Src/platform/user_periph_setup.c`
里的 `APP_UART` 配置（SK 板默认是 UART0）。

```bash
# Linux
screen /dev/ttyUSB0 115200
# 或者
minicom -D /dev/ttyUSB0 -b 115200
```

## 3. 上电应该看到两段

```
tinyml 自检通过：16 条 golden vector 逐位一致
── 推理耗时（实测，主频 64000000 Hz）──
  CNN   首次 xxxxx 周期 = xxx us（占空比 x/1000，按每秒一窗）
  CNN   均值 xxxxx 周期 = xxx us
```

### 第一段：自检

**这是上板之后唯一重要的一件事，比准确率重要。**

golden vector 是导出模型时 PC 上算好的「这个输入必须得到这个输出」。
板上重算一遍，逐字节比。

- **通过** → 工具链、编译选项、模型导出这三层全对。后面看到的任何准确率
  才是模型本身的准确率。
- **失败** → 串口上会直接打出按什么顺序排查。**先别怀疑模型**：
  1. 编译选项漏了 `-ffp-contract=off`，或者别处塞了 `-ffast-math`；
  2. 烧进去的 `tm_*.c` 跟 PC 上验过的不是同一份（对一下模型指纹）；
  3. int 宽度/对齐的假设在这个编译器上不成立。

自检没过的话固件会**主动不开始推理**。让一块算错的板子安安静静地上报错误数据，
比它直接不工作糟得多——后端统计会被污染，而且没人知道。

### 第二段：耗时

这个数是**板子自己用 DWT 周期计数器量的**，不是估的。

- **首次** 是 cache 冷的那一次。产品实际场景就是每秒醒一次、中间睡着，
  所以**首次那个数才是要拿来算功耗的**，均值只用来看抖动。
- **占空比（千分之几）** 直接回答功耗问题：它就是 CPU 醒着的时间占比。

如果打印的是
```
测速跳过：DWT 周期计数器没走（没接调试时钟？）
```
那是计数器不可用，**不是"推理耗时 0"**。一个好得离谱的数比一条报错更容易被当真，
所以固件宁可跳过也不报 0。

## 4. 然后才是看效果

自检过了，再往下：喂真实 IMU 数据，看识别结果。

这一步之前可以先在服务器上看——`python service/serve.py` 起的那个页面跑的是
**同一份 C**，而且 `tm_invoke` 全程整数、逐位结果跟指令集无关，
所以 x86 上验过的推理部分等于板上验过。板子要补的只有 `tm_prep` 里那 128 次
浮点运算（走各自平台的 libm），而 golden vector 自检覆盖不到它——
所以第 3 步那个自检**从 `tm_invoke` 开始，不含 `tm_prep`**，这是有意的：
混在一起的话，一旦对不上，分不清是量化错了还是推理错了。

## 常见问题

**烧完没有任何输出**
多半是烧录地址错了（用 `.bin` 时）。改用 `.hex` 重烧一次，地址是它自带的。
也看一下串口引脚和波特率。

**自检说「一条 golden vector 都没有」**
导出时没生成 `tm_golden.h`，或者编译时 `TM_HAS_CNN` / `TM_HAS_RF` 没定义对。
这**不算通过**——固件会当成失败处理。

**flash 不够**
链接脚本里 FLASH 区写的是 8MB（那是内存映射窗口，不是真实容量），
所以**超出 512KB 链接不会报错**。必须自己看产物 README 里 `text` 那个数。
模型太大的话，看 `export_cnn.py` 打印的逐层占比——
一维卷积的权重是 `out_ch × in_ch × k`，最后一层通常一家独大（实测占 77%），
只收窄那一层就能省掉大部分。
