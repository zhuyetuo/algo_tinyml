# 运行内存和 cache：flash 之外的两笔账

## 一、模型**不占运行内存**

这一条值得先说，因为它让"模型多大"这个问题的性质变了。

树的那几个数组是 `const`，链接之后落在 flash 里。从真实链出来的镜像里查：

```
$ arm-none-eabi-nm tinyml_app.elf | grep tm_forest
01016c70 000008e8 t tm_forest_left     ← 地址 0x0101xxxx = flash 区，段是 t(.text)
01017558 000008e8 t tm_forest_thr
010155b4 00000dd4 t tm_forest_leaf
```

GR5513 的 flash 是**内存映射**的（从 `0x01002000` 起），CPU 直接读，不用先搬进 RAM。
所以**一个 400KB 的模型占 0 字节运行内存**。RAM 用量跟模型大小无关。

## 二、运行内存实际用多少（按真实配置实测）

16 点窗口 × 8 通道 × 193 维特征 × 5 分类，`arm-none-eabi-gcc -Os`：

| | RAM (bss) | flash (text) |
|---|---|---|
| `tm_features.c` 的临时缓冲 | **1,168 B** | 3,088 B |
| `tm_gbdt.c` | 0 | 324 B |
| `tm_forest.c` | 0 | 202 B |
| `tm_window.c` | 0 | 326 B |
| `tm_feat_cfg.c`（窗/旋转因子表） | 0 | 188 B |

加上应用层要自己开的缓冲：

| | |
|---|---|
| 窗口环形缓冲 `float[8][16]` | 512 B |
| 出窗用的副本 | 512 B |
| 特征向量 `float[193]` | 772 B |
| margin `float[5]` | 20 B |
| **合计（含上面的 1,168）** | **约 2,984 B ≈ 2.9 KB** |

GR5513 应用可用 112 KB，BLE 协议栈基线占 22 KB。**我们这部分 2.9 KB，
不是瓶颈，而且模型再大也不会涨。**

> 注：`tm_features` 的 1,168 B 是按 `TM_FEAT_MAX_T=16` 编的。默认上限 64 时是
> 4,624 B——**按实际窗口长度设这个宏能省四分之三**。

## 三、真正被忽略的那笔账：**8KB cache**

模型不占 RAM，但它在 flash 里，而 GR5513 只有 **8KB cache**。
树遍历是**随机访存**——每个节点往哪走取决于上一个节点的比较结果，
硬件预取帮不上忙。

### 现在的布局（SoA）有个 4 倍的浪费

导出的是 `feat[]`、`thr[]`、`left[]`、`right[]` 四个独立数组。
访问**一个节点**要碰 4 个相距几百 KB 的地址 = **4 条 cache line**。

| | 每次推理要读的 flash |
|---|---|
| 5 分类 200 轮，SoA | 875 KB |
| 5 分类 200 轮，**AoS**（一个节点 6 字节连续） | 219 KB |
| 二分类 200 轮，SoA | 175 KB |
| 二分类 200 轮，**AoS** | **44 KB** |

（按深度 6 ≈ 7 个节点/棵、cache line 32 B 估。line 大小要在板上确认。）

**改成 AoS 是 4 倍改善，而且跟模型大小无关**——它纯粹是布局问题。
这比紧凑编码那 2.8 倍的体积压缩更值钱，因为它省的是**每次推理的 flash 读**，
而 flash 读是要耗电的。

所以我原来打算做的"紧凑编码"要改一下设计：**同时从 SoA 换成 AoS**。
两件事一起做，收益是 2.8 倍体积 + 4 倍访存。

### 模型总量 vs cache：只有很小的模型才有质变

| | 体积 | vs 8KB cache |
|---|---|---|
| 5 分类 200 轮（紧凑） | 401 KB | 50 倍 |
| 二分类 200 轮（紧凑） | 80 KB | 10 倍 |
| 二分类 15 轮（紧凑） | 6 KB | **整个装得进 cache** |

装得进 cache 的话，第二次之后的推理几乎不读 flash，耗时和功耗会有**台阶式**的下降。
但 15 轮的抓挠 F1 只有 0.561，为了这个台阶牺牲掉那么多准确率不值。

**结论：cache 这条不构成"必须做到 8KB 以内"，但它是一个额外的、独立于 flash 容量的
"越小越省电"的理由**，而且它让 AoS 这个改动的优先级排到了紧凑编码前面。

### 还没测的

上面全是按访存次数推的。**真实的耗时和功耗要在板上测**——
flash 读的实际延迟、cache line 大小、以及 GR551x 的 flash 控制器有没有预取，
都得看手册或者实测。方法在 [gr551x/README.md](../firmware/gr551x/README.md)
（DWT 周期计数器）。
