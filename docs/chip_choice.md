# 推理放哪颗芯片

项圈上有四颗芯片：

| 芯片 | 角色 | 核 | 存储 |
|---|---|---|---|
| **GR5513BENDU**（Goodix GR551x） | BLE 5.1 | Cortex-**M4F** @64MHz，带 FPU + DSP 指令 | 512KB Flash / 128KB RAM（**含蓝牙协议栈**） |
| **nRF9151**（Nordic SiP） | LTE-M/NB-IoT + GNSS | Cortex-M33 @64MHz，带 FPU + DSP | 1MB Flash / 256KB RAM |
| **nRF7002** | Wi-Fi 6 | **没有通用 MCU** | — |
| **QMI8658B** | 6 轴 IMU（acc + gyro） | — | 自带 FIFO / wake-on-motion |

## 结论：推理放 GR5513

**nRF7002 不是候选。** 它是 Wi-Fi 6 companion IC，只做 802.11 的 PHY/MAC，
协议栈上层和应用都跑在外挂的 host MCU 上，靠 QSPI/SPI 挂过去。它连跑代码的地方都没有。

**GR5513 vs nRF9151**，三条理由，按重要性排：

1. **GR5513 本来就醒着，而且离 IMU 最近。** QMI8658B 挂在谁身上谁做推理最省电——
   数据不用跨芯片搬。
2. **端侧推理省的是射频，不是算力。** IMU 行为识别 25–50Hz、2–4 秒窗口，一次推理在
   M4F 上是毫秒级，占空比不到 1%，折合平均十几 µA，跟 BLE 广播比可以忽略。端侧推理
   真正的价值是**把「每秒几百个采样点」压成「一天几条事件」**，让射频不用开。把这个
   判断放到 nRF9151 上，等于为了省电去唤醒整个项目里最耗电的那颗芯片，方向反了。
3. **nRF9151 资源多，但多得没用。** 1MB/256KB 对一个 IMU 行为模型是奢侈——本仓库
   默认结构量化完是 768 个 int8 权重，不到 1KB。用不上的余量不构成选它的理由，
   而它的蜂窝代价是实打实的。

**nRF9151 的正确角色**：平时睡，GR5513 判出事件了再叫醒它上报（或者攒一批一天传一次）。
GNSS 同理，事件触发再定位。

## 上板之前要先量的一件事

GR5513 的 128KB RAM / 512KB Flash 是**跟 BLE 协议栈共用**的，留给应用的实际余量
取决于现在固件用了哪些 profile，**这个数必须自己量**（GR551x SDK 编出来看 map 文件），
不能按标称值规划。

建议门槛：应用可用 **RAM ≥ 32KB、Flash ≥ 128KB**。本仓库默认结构的实际占用：

- 权重 768 B（int8）+ bias/乘子 27×3×4 B ≈ 1.2 KB Flash
- 推理临时缓冲 `TM_ARENA_BYTES` = 960 B（两块乒乓，各 480 B）
- 窗口环形缓冲 n_ch × n_t = 6 × 64 = 384 B
- 合计 RAM 峰值约 1.4 KB

离 32KB 还差得远。**如果量出来卡得很死**，方案不用推翻，只是模型要压到更简
（传统特征 + 小分类器，而不是 CNN），或者让 GR5513 只做特征提取、判决挪走。

## 采样怎么取

QMI8658B 自带 FIFO 和 wake-on-motion。**用 FIFO 水位中断批量取数**，让 M4F 大部分
时间睡着，比定时器逐点取省得多。具体 FIFO 深度查手册再定 batch 大小——这个数
本文档不写，因为写错了比不写更糟。
